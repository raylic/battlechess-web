# 皇家战棋 · Web（Vite + React + TS）

原作：[MemoryD/BattleChess](https://github.com/MemoryD/BattleChess)（Python + pygame + twisted，2019）。
本仓库是它的 Web 复刻：**规则内核逐行迁移，视图层重写为 React**。没有服务端、没有账号、没有积分。

本目录**自给自足**：`package.json` / `pnpm-lock.yaml` / `node_modules` / `public/assets` / 各类配置都在自己目录内，不 import 任何外部文件，也没有 workspace。实测把整个目录拷到仓库外，`pnpm install && pnpm test && pnpm build` 全过。

## 1. 怎么跑

```sh
cd battlechess-web
pnpm install
pnpm dev            # http://localhost:5173/battlechess-web/
pnpm test           # vitest run
pnpm coverage       # 覆盖率报告
pnpm build          # tsc -b && vite build
pnpm assets         # 从原仓库重新拉取美术素材（只拷用到的那 12 张）⚠️ 见 §9
```

### URL 参数

| 参数 | 作用 |
|---|---|
| `?mode=ai` | 直接开人机对局 |
| `?mode=hotseat` | 直接开单机热座（一个人控制两方） |
| `?mode=dual&side=blue&seed=123` | 双窗口：以蓝方视角加入 123 号棋局 |
| `?seed=123` | 指定棋盘种子（同种子 = 同一盘棋） |
| `?debug=1` | 右下角显示"真面目"面板（只有单机模式拿得到真相） |
| `?ai=` | 电脑档位：`search`（默认，PIMC 搜索=老师）/ `greedy`（一步贪心，最弱）/ `net`（神经网络，暂不可用）。旧名 `pimc` 是 `search` 的别名 |

## 2. 怎么玩

| 开始界面按钮 | 实际模式 | 说明 |
|---|---|---|
| 本地对战 | **单人 vs 电脑** | 你执红先手；AI 只看得到蓝方视角，和你受同样的信息限制 |
| 联网对战 | **双人 · 两个视角** | 点一下自动再开一个窗口：本窗口红方、新窗口蓝方，各看各的视角，只能在自己的回合操作 |

> 双窗口基于 `SharedWorker`（Chrome / Firefox / Safari 16.4+）。若浏览器拦截弹窗，手动打开开始界面显示的 URL：`?mode=dual&side=blue&seed=<种子>`。

### 规则

- 棋盘 6×6，**36 格开局全部摆满、全部背面朝上**。背面棋子红蓝共用一张图：**翻之前谁也不知道它是谁的**（双盲）。
- 每方 18 子：国王 1、将军 1、骑士 2、弓箭手 2、禁卫军 4、刺客 8。等级越小越强。
- 轮到你时**二选一**（各算一步）：① 翻开任意一张背面棋子（包括对方的）；② 移动自己已翻开的棋子，上下左右**走一格**，目标是空格或可吃的敌子。
- 吃子：目标必须已翻开且是敌方；`自己等级 <= 对方等级` 即可吃。**刺客能吃国王，国王吃不了刺客。**
- 结束：一方被吃光 / 双方各剩 1 子比大小 / 连续 30 步无吃子无翻棋判和 / 认输（需走过 20 步）。

## 3. 架构

```
authority（持有真相的纯函数状态机，core/authority.ts）
   │  只接受 action（类型是 unknown，边界处显式校验），只发出 state(已按视角投影) + reject
   ▼
transport（local 直连 / SharedWorker；将来换 WebSocket 不改规则与视图）
   ▼
view:red / view:blue（各自只有 viewFor(side) 的投影）
   ▼
React 组件（纯展示 + 纯交互策略，不含规则）
```

```
src/
├── core/                纯逻辑，零 DOM 依赖，跑在 node 环境下
│   ├── pieces.ts        兵种、每方数量、克制矩阵（含刺客/国王特例）
│   ├── rng.ts           mulberry32 种子随机
│   ├── board.ts         36 子洗牌落位（双方数量严格对称）
│   ├── rules.ts         legalActions / movesFrom
│   ├── judge.ts         四条结束条件 + stalemate 兜底
│   ├── reduce.ts        applyAction：唯一能改状态的地方（action: unknown）
│   ├── visibility.ts    viewFor(state, side)：隐藏信息只在这一层发生
│   ├── ai.ts            简易 AI（只用 ViewState，绝不偷看真相）
│   ├── authority.ts     权威：持有真相、校验回合、下发投影
│   └── test-helpers.ts  紧凑摆棋记号（'r0' / 'b3*' / '.'），仅测试用
├── transport/           local.ts（单机）/ worker.ts（SharedWorker）
├── worker/              authority.worker.ts
├── game/
│   ├── useSession.ts    会话生命周期：建会话 / 回开始界面 / 再来一局
│   ├── useGame.ts       订阅 client → view / toast
│   ├── useAi.ts         AI 侧 client + 档位选择 + 思考定时器
│   ├── netLoader.ts     网络权重懒加载（失败回退）
│   ├── useEatenGhosts.ts 被吃棋子的淡出幽灵
│   ├── useFitScale.ts   整个 1000x650 舞台按视口等比缩放
│   ├── geometry.ts      棋盘几何常量（CSS 变量的单一事实来源）
│   ├── boardInteraction.ts 点击策略 + 高亮（纯函数）
│   ├── panel.ts         侧栏棋子面板：每方 5 行、存活/没翻起/被吃（纯函数）
│   └── hudText.ts       HUD 文案 + 结算面板映射（纯函数）
└── components/          Board / Piece / Hud / StartScreen / ResultModal / Toast / TruthPanel
```

### 不变量

- **隐藏信息只发生在 `visibility.ts` 一个函数里。** 组件没有"要不要隐藏"的判断 —— 它拿到的数据里就没有暗子身份。
- **合法着法由权威算好随视角下发**，组件不重复实现规则，也不能自己造合法着法。
- **`core/` 不 import 任何 DOM** → 规则可以在 node 环境里跑 1000 局自对弈。
- **AI（含神经网络）只吃 `ViewState`，结构上就拿不到真相。** 训练数据也走同一条投影路径，
  否则训出来的网络会依赖它在上网时拿不到的信息。

### 相对原生版，React 化时做的几处结构改动

| 改动 | 为什么 |
|---|---|
| `dire`（棋子朝向）从 UI 挪回核心状态 | 原版存在 `boardView` 的私有 Map 里；挪进 `Piece` 后组件彻底无状态，且朝向也能被规则测试覆盖 |
| 点击策略抽成 `resolveClick()` 纯函数 | 原来埋在 `handleClick` 里，是"不是自己回合/终局后不能操作"两条守卫**零测试**的根源 |
| HUD 文案与结算面板映射抽成纯函数 | "赢了显示失败""按钮该亮不亮"这类问题现在能被单测钉死 |
| 被吃棋子的淡出改成 `useEatenGhosts` | React 里棋子消失会立刻卸载，淡出必须显式记住"刚消失的那些" |
| 几何常量集中在 `geometry.ts` 并写入 CSS 变量 | CSS 与 JS 不会各写一份 88px |

## 4. 有意偏离原版的地方（4 处，都可以改回来）

| # | 原版行为 | 这里 | 理由 |
|---|---|---|---|
| 1 | 残局同级时**判红胜**（代码先算 `red.eat(blue)`） | **判和棋** | 原版是执行顺序带来的不对称，不是规则 |
| 2 | 某方完全无子可动时**无限空转** | **判和棋**（`stalemate`） | 单机没有计时规则，不兜底会卡死 |
| 3 | 终局仍扣着未翻开的棋子 | **终局全亮** | 当复盘用，此时无信息可藏 |
| 4 | 20 秒/步、3 次超时判负 | **不做** | 本期无真人实时对手 |

另外 AI 加了一条"无子可吃时朝最近敌子靠拢"的启发式：没有它时 AI 会在残局和对手随机游走，**92% 的对局撞上 30 步和棋规则**；加上之后降到 ~34%。

## 5. 双盲口径

原版是**双盲**（`unopen.png` 红蓝共用一张），本期照此实现。必然结果：**两个视角的信息完全对称**，`viewFor('red')` 与 `viewFor('blue')` 只差 `you` 和 `legal`（谁能操作）—— 这是玩法固有性质，测试里专门编码了这条。

`visibility.ts` 里留了另一个口径 `OWN_KNOWN`（自己的暗子自己可见），只差一个常量：

```ts
export const DEFAULT_POLICY: Policy = POLICY.OWN_KNOWN;
```

### 真浏览器点击自检（不在 `pnpm test` 里）

```sh

pnpm click:check    # Chrome headless + CDP，派发真实鼠标事件
```

它守的是 jsdom **结构性覆盖不到**的一类问题：`fireEvent.click` 是直接派发到目标元素的，绕开了浏览器的命中测试 —— 于是"有一层东西盖在棋盘上方"在单测里完全看不出来，真机上却一个子都点不动（真实翻过车：`#heads` / `#controls` 是 `inset:0` 铺满舞台、DOM 顺序又排在 Board 之后，接管了棋盘上的全部点击）。脚本会真实点击并断言翻棋 / 选中 / 吃子走子 / 认输按钮，另外做一组 A/B 对照：把覆盖层的 `pointer-events` 改回 `auto` 就能复现"点不动"。

需要本机有 Chrome / Chromium；没有就跳过（退出码 2 并提示）。


|---|---|---|---|

### 为什么是 PIMC

本作是**双盲暗棋**：公开信息 = 已翻开的棋子 + 双方各等级剩余数量 + 格子占用。
而开局棋子是均匀洗牌的，所以"与当前情报一致的世界"就是「把剩余棋子池均匀随机地铺到
未翻开的格子上」—— 后验可以**精确采样**，不需要近似。于是：对 K 个采样世界各做一次
完全信息搜索，再把同一个动作在 K 个世界里的分数取平均。

这一步顺手把 PIMC 的经典病（信息泄漏）抹平了：搜索在单个世界里"知道"每个暗子是谁，
会故意去翻自己的国王；但那个动作在别的世界里可能是翻对方的刺客，跨世界平均之后就
退化成「翻这一格到底值不值」的期望值 —— 这正是我们想要的。

### 三个把它变强的具体机关（都是实际对局里发现症状后加的）

| 症状 | 机关 |
|---|---|
| "看不到两步之后" | 自动深度：开局 3～4 层，残局 6～8 层（子越少分支越小，同样的预算能搜更深） |
| "偶尔莫名其妙送一个子" | ① 吃子延伸（quiescence）；② **两段式预算**（见下） |
| "没有目的性、走一步看一步" | 追击与和棋倒计时：领先时优势会被"30 步无吃子判和"收缩，逼它去接触 |
| "一直跟玩家来回绕圈" | **循环惩罚**（见下） |
| 明显要输还硬走到底 | **认输**（见下） |
| 开局 36 个翻棋吃掉 95% 的预算 | **翻棋归类**：双盲下各暗格"是谁"的分布相同，差别只在邻接几何，归成几类只搜代表 |

性能上还有两条硬指标：搜索内部用 `core/searchCore.ts` 的 **make/unmake**（而不是
`reduce.applyAction` 的不可变 clone），以及**零分配的着法生成**。第一版每节点约 80 次分配、
15 微秒；换掉之后同一批节点快了一个量级 —— 这是"能搜到 6～8 层"的前提。

### 两段式预算：为什么"平均分预算"反而会让它送子

这是排查得最久的一个 bug，值得单独记一笔。

症状：老师偶尔把自己的**国王**走到对方国王旁边白送。起因不是评估函数写反了，而是
**每根动作 400 节点的预算不够走到能看见错误的那一层**。实测同一个局面（seed 9000 第107步）：

| 搜到第几层 | 国王 1,3→2,3 | 刺客 2,2→2,3（正解） |
|---|---|---|
| 1 层 | **+271** | +268 |
| 2 层 | **+260** | −94 |
| 3 层 | **+268** | +253 |
| **4 层** | **−83** | **+328** |

"国王走过去"其实是个**国王互换**（我刺客能吃回来），1～3 层看都是小赚，要到第 4 层才看得出
后续吃亏。而 400 节点只够走到 3 层 —— 也就是说：**预算不够时，有些错误在搜索视野里根本不存在**。

做法改成两段：先用小预算（`nodeBudget`，默认 400）把所有动作排一遍，再把排名靠前的
`deepenWidth` 个（默认 5）用 `deepenBudget`（默认 2400）重算。节点花在真正有可能赢的那几手上，
而不是给每个动作平均分 —— 平均分意味着谁都走不到底。实测战绩从 10胜1负1和 变成 12胜0负0和，
平均步数还少了 13 步（会收尾了）。

### "自投罗网"：把子走到只剩被吃（`ownThreatFull`）

**症状**（人类对局，16 盘 / 700 多手实测）：它会把一个子主动走到"**下一手必然被吃、换不回来**"的格子，
而当时明明有 10 几个不糟的选择。16 盘里 **9 次**，其中 **8 次下一手真被吃**：

```
第15盘 第35手 骑士(0,4)→(1,4)   走完就被 将军(2,4) 吃(亏160) · 另有 13 个不糟的选择
第7盘  第109手 将军(0,5)→(1,5)  走完就被 将军(1,4) 吃(亏300) · 另有 13 个
第2盘  第41手 国王(2,3)→(1,3)   走完就被 国王(1,4) 吃(亏1000) · 另有 12 个
```

**病根**就一行代码 —— 威胁项对自己人也打半价：

```ts
threat += (mine ? -value : value) * HANGING_WEIGHT; // 0.5
```

于是"吃一个 60 分的禁卫军、白送你一个 160 分的骑士"在它眼里是 `+60 − 80 = −20`（约等于不亏），
真值是 −100。

**这里有个坑**：直接把 `HANGING_WEIGHT` 提到 1.0 会让棋力变**差**
（同种子 12 局：12 胜 0 负 0 和 → 8 胜 1 负 3 和）。因为那样**敌方**挂子也变满价，
它就觉得"这子迟早是我的"，反而不急着吃，把赢棋走成了和棋。

**正确的做法是只罚自己、不奖励自己**（`ownThreatFull`，悲观评估）：

- 我方挂着的子按 **全价** 扣（默认对手一定会来吃）
- 敌方挂着的子仍按 **半价** 加（不去抢自己还没吃到的东西）

**但是它的整体棋力是下降的，所以默认关闭**（这条是这次踩的坑，记下来免得重试）：

| 测量（同配置同种子） | 关闭 | 打开 |
|---|---|---|
| 自对弈 40 局 | **61.3%** | 38.7%（14胜5负21和） |
| 对贪心 16 局 | **90.6%** | 81.2% |
| 9 次"自投罗网"被改掉 | 2/9 | 6/9 |

自对弈里 21 局判和、19 局认输、**0 局吃光** —— 典型的"过度谨慎、不敢交换、赢不下来"。
跟把 `HANGING_WEIGHT` 整体提到 1.0 的失败是同一个病。

教训：**"坏棋清单被修掉"是个有偏指标** —— 让引擎过度悲观，当然能修掉那几手。
同一批数据里 `kingFullPrice`（挂着的国王按 1000 而不是 500）没有额外收益，
`hiddenThreat`（暗子被攻击也算威胁）反而更差（5/9），所以两者默认都关着，只留开关和结论。

### 安全闸：不许把子走到"看得见的白吃"上（`safetyGate`）

人类对局的 16 盘里有 **9 次**它主动把子走到"下一手必然被已翻开的敌子白吃"的格子，其中 **8 次下一手真被吃**，
而每次都有 10 几个不糟的选择。诊断后确认了两件事：

- 这些手在 **1~2 层是明确坏棋**（排 13~19/20，差 100~1000 分），是**3 层搜索的"补偿幻觉"**把它抬上去的；
- 同一手在不同采样世界下分数波动 **±208**，而它和最好手之间只差 ~100 → 6 个世界平均根本分不开。

所以这条规则**不碰评分**，只做否决：

1. 用**纯公开信息**（已翻开的攻击者/被攻击者）算"我方白吃暴露"——零采样噪声；
2. 走完之后暴露**变大**（且吃不回来）的着法进黑名单；
3. **豁免**：如果它比"最好的安全着法"高出 `safetyGate`（250）以上，那算真弃子，放行；
   （150 时漏过一手：+1420 的必胜局面里它靠"高 171 分"把将军送到对方将军嘴边 ——
   净多 21 分，而 6 世界平均的噪声是 ±208。250 拦住了，且误伤率不变。）
4. 如果所有着法都不安全，不拦（落后局面里本来就全是坏选择）。

实测：9 个"自投罗网"**拦住 7 个**；在 **74 个普通决策点**上只改了 **1 次（1%）**——所以它不会像"调评估"那样
把整个棋风改掉（对比：`ownThreatFull` 每手都变，棋力掉了 20 个点）。

两个已知漏网（都不是闸门的 bug，记下来）：

- **国王送吃**：搜索给那手 −714、最好的安全着法 −1102（差 388 > 150），被当成"真弃子"放行 —— 这属于搜索幻觉；
- **带"吃回来"的落点**：落点旁边的我方子理论上吃得回攻击者（`recap` 计入净亏），于是净亏算成 0，不拦。

### 循环惩罚：不许来回走

`reduce.publicKey(state)` 给每个局面算一个**公开指纹**（轮到谁 + 每格是空的/暗的/翻开的几级谁），
**故意不含** noEat / step 这些计数器 —— 这样"同一颗子走回去"在几步之后就会撞上同一个指纹。
`viewFor` 把最近 32 步的指纹放进 `ViewState.recent`（公开知识，K 个世界共用同一份，
不破坏信息边界），根节点上如果某个动作会把盘面带回其中任何一个，就从它的分数里扣
`repeatPenalty`（默认 150：比一个弓箭手大、比一个将军小 —— 压得住绕圈，但不会为了"不重复"白丢一个将军）。

实测：老师"走回旧局面"的步数从 23/746 变成 **0/764**。

### 认输：明显要输就不拖

规则允许后（走过 20 步）如果**最好的动作**的跨世界平均分都低于 `-resignMargin`，就认输。
看"最好的动作"而不是平均 —— 只要能找到一手还能拖的棋（比如守和）就不认；
分数里本来就含"和棋倒计时收缩"，所以接近 30 步无吃子的局面分数会被拉向 0，能守和自然不认。

阈值是拿对局标定的（12 局，老师 vs 贪心）：

| resignMargin | 战绩 | 认输次数 |
|---|---|---|
| 关闭 | **12胜0负0和** | 0 |
| 1000 | 11胜1负0和 | 1 |
| 600 | **7胜5负0和** | 5 |

**600 太松**（落后一个小级别的子力就认，第 20 步就认输成了常态）；默认取 1400
（大致"落后一个国王"），宁少认不乱认。传 `Infinity` 即关闭。

### 神经网络是怎么来的

训练侧在仓库外（`~/code/game/train`，Python + PyTorch），流程与命令见 `train/README.md`：

```
TS 自对弈（老师 = PIMC，标签走和线上一样的编码路径）
   ↓ 二进制数据集
PyTorch 训策略/价值双头（9.6 万参数，374 KB）
   ↓ weights/net-v1.bin
check-parity.ts 逐元素核对 TS 手写前向 ≡ PyTorch   ← 必须过
   ↓
arena.ts 新 AI vs 旧 AI 对抗验收
```

**为什么必须有 `check-parity.ts`**：它抓到过两个 bug（线性层权重按 `[in][out]` 取、
卷积核方向写反），两个都会让棋力"看起来还行"，但模型其实完全错位 —— 光看胜率查不出来。

**当前状态：还不合格。** 训练管线全通（前向与 PyTorch 逐元素一致，差 1e-7），但蒸馏出来的
棋力只有对贪心 13%（约等于随机）—— 根因是老师的逐动作偏好本身被采样噪声主导（软标签平均熵
2.56，接近均匀 2.93），用线性模型 / MLP / 卷积网分别试都学不动，说明不是网络容量问题。
所以默认档是老师（`search`），网络档只作为可选项留着。

### 浏览器里玩 vs 生成训练数据：用的是两套参数

`DEFAULT_SEARCH`（`search.ts`）给训练/验收用最强调参：`worlds 8 / nodeBudget 400 /
deepenWidth 5 / deepenBudget 2400`（约 500ms/手）。浏览器里跟人下用的是
`useAi.think()` 的 `worlds 6 / deepenWidth 5 / deepenBudget 2400`（约 370ms/手）——
同样的两段式结构，只把世界数从 8 降到 6，换回约 1/4 的时间
（这套参数的独立验收：对旧贪心 10 局 **9胜0负1和**，平均 126 步）。

### 同一个 AI 的两个版本怎么对打（arena）

`arena.ts` 支持给两边分别加搜索选项，所以"v1 vs v2"能在同一个进程里跑，只有那一个开关不同：

```bash
pnpm exec tsx scripts/arena.ts --a search --b search --games 60 \
  --worlds 4 --budget 400 --deepen-width 3 --deepen-budget 1200 \
  --a-opt '' --b-opt splitQuiescenceBudget=true
```

**这类自对弈是弱仪器，别被它骗**：两个水平相同的引擎互殴会大量和棋/认输 —— 实测 60 局里
34 局 30 步判和、26 局认输、**0 局吃光**，噪声很大。要看真差距，要么拿一个共同参照物
（比如贪心）分别打，要么把局数拉到几百局。

已经用它判过一个假设（`splitQuiescenceBudget`：让吃子延伸用独立预算，好让主搜索真的走到
名义深度）：**60 局 14胜12负34和 = 51.7% vs 48.3%，没有收益，而且节点更多**，所以默认关闭。
开关和这个结论都留在代码注释里，免得以后重试。

### 对局记录（复盘坏棋用）

终局弹窗上有两个按钮：**⭐ 标记这局有问题** 和 **导出对局记录**。记录存在 localStorage
（`gameLog.ts`，上限 100 盘），每盘只存 **「种子 + 动作序列」**：整盘棋是确定性的，
`createState(seed)` 加上动作序列就能完整重放（包括每一步的真相），存真相反而更占地方。
导出的 JSON 拿给 AI 就能定位"第几步的哪一手是坏棋"。

## 8. 已知限制

- **纯前端防不住作弊**：真相 state 就在浏览器内存里，devtools 可见。双窗口模式把门槛抬高一档（真相在 SharedWorker 里），但不是安全边界。
- 双窗口要求同浏览器同源且支持 `SharedWorker`；不支持时自动退回单机热座。
- 不做计时/超时判负，对局可以无限思考。
- 网络档的权重（`public/models/net-v1.bin`，约 374 KB）是**懒加载**的：拿不到（离线首访、文件缺失）会退回搜索档，不会卡住棋盘。
- 像素级效果（透视角度、棋子重叠/裁切、字重）只能靠眼睛确认。`pnpm click:check` 能把"点击能不能落到棋子上"自动化，但"画面对不对"得看图 —— 本次两个真实 bug（覆盖层吃掉棋盘点击、`--piece-z` 太小导致棋子下半身被格子盖住）都是靠它 + Chrome 截图发现的。

## 10. 部署与缓存

### base path

本站按 **GitHub Pages 项目页**（`https://<user>.github.io/battlechess-web/`）部署，所以 `vite.config.ts` 里配了：

```ts
base: process.env.BASE_PATH ?? '/battlechess-web/'
```

- **`base` 对 dev server 同样生效** —— 本地地址是 `http://localhost:5173/battlechess-web/`（访问根路径会 302 跳过去，所以旧书签还能用）。开发与生产同路径，base 写错在本地就能发现。
- Vite 会自动给 `index.html` 和 CSS 里的 `url(...)` 加前缀；但 **JSX 里写成字符串的 `src` 不会**，那几处必须自己用 `import.meta.env.BASE_URL`（见 `Hud.tsx` / `GameScreen.tsx` / `StartScreen.tsx`）。
- 改传到 `<user>.github.io` 用户主页或绑自定义域名时，把 base 改回 `/`（或用 `BASE_PATH=/ pnpm build`）。

### 客户端缓存（Service Worker）

GitHub Pages **不允许自定义响应头** —— 全站固定 `Cache-Control: max-age=600`。所以那 12 张不带内容 hash 的素材每 10 分钟就要重新校验一次，换了内容还最长吃 10 分钟旧图。`public/sw.js` 是 Pages 上唯一能真正控制客户端缓存的机制：

- 导航请求（HTML）→ **网络优先**，失败回退缓存 → 永远先拿最新版，断网也能进游戏
- 其余同源静态资源 → **缓存优先 + 后台更新**（stale-while-revalidate）
- 只在**生产构建**注册（`src/registerSw.ts`），开发期不注册，免得缓存和 HMR 打架
- `sw.js` 里的 `VERSION` **只影响旧缓存清理，不影响正确性**：不 bump 也不会出错，只是带 hash 的 JS/CSS 旧文件会一直留在 Cache Storage 里（每版约 250 KB）。

### 构建产物

`dist/` 约 **2.04 MB** = 图片 1.79 MB（12 张素材 1.64 MB + 5 个图标 0.15 MB）+ 代码 0.25 MB。`dist` 在 `.gitignore` 里，由 CI 发布，不进版本库。

## 11. 移动端 / PWA / 强制横屏

### 可安装（PWA）

`public/manifest.webmanifest` + `public/assets/` 下的 192 / 512 / maskable / apple-touch 四个 PNG。都是手写的，**没有引入 `vite-plugin-pwa` / workbox** —— 项目只有 react + react-dom 两个依赖，不为这点事破例。

manifest 里的 URL **全是相对路径**（`start_url: "./"`、图标 `src: "assets/xxx.png"`），这不是偷懒：

- Vite 只改写 `index.html` 和 `src/` 里的引用，**`public/` 下的文件是原样拷贝的**，manifest 拿不到 `base`；
- 相对 URL 按“manifest 自身的位置”解析，所以它天然跟着 `base` 走 —— `BASE_PATH=/ pnpm build` 出来的包也是对的；
- 代价是 `src/pwa.test.ts` 里有一条测试专门盯着“别在 manifest 里写绝对路径”。

图标由 `scripts/make-icons.py` 生成，顺手做了两件好事：给 `apple-touch-icon` 和 maskable 版本**铺上 `#0d1117` 底**（iOS 会把透明像素渲成黑色，Android 会把 maskable 裁掉一圈），以及**量化到 256 色** —— 扁色卡通肉眼无差，整套图标 810 KB → 153 KB。

### 强制横屏：三层，逐层兜底

| 层 | 手段 | 什么时候真的有效 |
|---|---|---|
| 1 | `manifest.orientation: "landscape"` | **装到主屏后**的独立窗口。规范明说浏览器标签页里忽略（display mode = browser） |
| 2 | `screen.orientation.lock('landscape')`（`src/lockOrientation.ts`） | 支持且已独立窗口的浏览器。**iOS Safari 压根没实现这个方法**；Chrome 要求用户手势，所以代码在首次 `pointerdown` 时再补一刀，失败全程静默 |
| 3 | **竖屏遮罩**（`index.html` 的 `#rotate` + `styles.css` 的媒体查询） | **全平台、无需安装、不依赖 JS**。这才是真正兜底的那层 |

第 3 层为什么非要不可：舞台写死 1000×650（宽高比 1.538），390×844 的手机上 `--fit = min(390/1000, 844/650) = 0.39`，棋盘被缩成 **390×253、一格约 34px**，手指点不准；同一台机器横过来就是 `--fit = 0.60`。

几个刻意的取舍：

- **遮罩写在 `index.html` 而不是 React 组件里**：JS 还没挂载（甚至挂了）的时候，竖屏用户看到的就已经是提示，而不是一个缩小的棋盘。
- **开关只有一句媒体查询**：`@media (orientation: portrait) and (pointer: coarse)`。`(pointer: coarse)` 是为了不误伤桌面 —— 桌面把窗口拉窄拉高不该弹这个。
- **遮罩 `pointer-events: none`**：纯提示、不拦事件。万一下面那句媒体查询判断偏了（某些触屏笔记本），用户不会被这层困住。
- **平板（iPad 竖屏）也会命中**，这是有意的：1000×650 在竖屏下上下全是黑边。真不想管平板，加一条 `(max-width: 900px)` 就行。
- **没做“竖屏时把舞台旋转 90°”**：那套是给“系统方向锁开着”的用户用的，得歪着头玩，v1 不做。

### 移动端手感补丁

`overscroll-behavior: none`（防下拉刷新 —— 全屏画布上误触一次就等于重开一局）、`touch-action: manipulation`（去掉双击缩放）、`user-select: none`、`-webkit-tap-highlight-color: transparent`、`viewport-fit=cover`（让底色铺到刘海区）。

### 自检

```sh
pnpm build && pnpm preview
pnpm pwa:check "http://localhost:4173/battlechess-web/?mode=hotseat&seed=42"
```

它用 CDP 模拟真机视口 + 触摸，实测四件事：Chrome 真的解析了 manifest（`Page.getAppManifest`，含每个图标 HEAD 200）、遮罩在「桌面横窗 / 桌面窄高窗 / 竖屏手机 / 横屏手机」四种情况下的显隐、`screen.orientation` 能力、SW 接管。

⚠️ **桌面那两条必须跑在触摸模拟之前**：CDP 的 `setTouchEmulationEnabled(false)` 不会把 `pointer: coarse` 干净地还原，之后测到的就是脏状态。（这个坑是在写这个脚本时真实踩到的：它一度报“桌面窄高窗也弹遮罩”，而实际代码是对的。）
